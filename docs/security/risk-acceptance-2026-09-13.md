# Risk acceptance - libuuid HIGH advisories in the runtime image

**Date:** 2026-09-13 - **Expires:** 2026-09-27 - **Scope:** container image `project-xray:*` only
**Reviewers:** founder (accountable) + red-team reviewer (turn 5 hardening loop)

## Why this exists

The `blocking-security` job of PR #32 (head `860d464`) **failed**: grype found
four HIGH advisories in `libuuid 2.42.1-r0`, inherited from the Alpine base of
`python:3.13-alpine`:

| CVE | Package | Severity | Fixed in | EPSS |
|---|---|---|---|---|
| CVE-2026-76642 | libuuid 2.42.1-r0 | High | 2.42.3-r0 | 0.2% |
| CVE-2026-78409 | libuuid 2.42.1-r0 | High | 2.42.3-r0 | 0.1% |
| CVE-2026-78408 | libuuid 2.42.1-r0 | High | 2.42.3-r1 | 0.1% |
| CVE-2026-78410 | libuuid 2.42.1-r0 | High | 2.42.3-r0 | <0.1% |

All other findings (python 3.13.15, busybox, nghttp2-libs) are Medium/Low and
do not trip `--fail-on high`.

## Remediation attempted first

The Dockerfile already runs `apk upgrade --no-cache` in **both** stages and
rebuilds with `docker build --pull`, i.e. the image takes the newest package
set the pinned Alpine branch serves. `util-linux 2.42.3-r0/-r1` is not served
by that branch yet, so the fix cannot be installed reproducibly today.
Pulling it from `edge` would make the build non-reproducible and would drag an
unpinned toolchain into a release artefact - a worse risk than the one below.

## Exposure analysis (why the residual risk is acceptable for 14 days)

1. **The application never calls libuuid.** UUIDs are generated by CPython's
   `uuid` module over `os.urandom`. `grep -rn "uuid" app/` shows no ctypes or
   subprocess use of util-linux; `uuidd`, `mount`, `blkid` and the rest of
   util-linux are not in the runtime layer.
2. **No attacker-controlled input reaches a libuuid entry point.** The three
   advisories concern parsing of on-disk superblock/uuid metadata by
   util-linux tooling, which the container never executes.
3. **Blast radius is bounded.** The container runs as non-root uid 10001, the
   application layer is read-only, and the preview deployment is a labelled
   synthetic-data environment with no customer PII.
4. **EPSS is <=0.2% for every accepted CVE** - no observed exploitation.

## Controls attached to this acceptance

- Suppressions in `.grype.yaml` are **CVE-scoped and package-scoped**
  (`package.name: libuuid`, `type: apk`) - a blanket ignore is rejected by CI.
- `scripts/check_grype_exceptions.py` now validates **every** file that can
  suppress a finding (previously it only read `security/grype-exceptions.yaml`,
  a file grype never loads - a real governance hole found in this turn) and
  **fails closed** the moment `2026-09-27` passes.
- `tests/test_grype_exceptions.py` proves the guard rejects expired,
  unapproved, undated and blanket suppressions.
- Weekly rebuild: on the first CI run after the base branch ships
  `util-linux 2.42.3-r0`, delete the four entries; the guard then reports
  "no active suppression".

## Rollback

Delete the `ignore:` block in `.grype.yaml`. CI returns to the previous
fail-on-high behaviour with zero suppressions.
